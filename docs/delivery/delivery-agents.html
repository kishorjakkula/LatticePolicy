LatticePolicy Delivery Agents

Approved by the product owner and implemented in pull request #382. The workflow lives in the repository at docs/delivery/WORKFLOW.md.

A tool-neutral, multi-agent workflow that takes a coding request from business analysis to validated deployment. It works the same whether Claude, Codex, Copilot, Cursor or another assistant writes the code, because the agents are role contracts and handoff files kept in the repository, not features of one product.

Summary

Your nine agents are the right backbone. I recommend keeping all of them and adding five things that real delivery teams in regulated insurance rely on: an orchestrator that runs the flow, test design before coding, an independent code reviewer, a security and compliance reviewer, and a knowledge curator. I also recommend three sizes of flow, so a one-line fix does not pass through eleven agents.

Each agent is a Markdown contract in the repo that states what it reads, what it must produce, what it may not do, and when it is done. Every stage writes its output to a work-package folder, so the next agent, a different AI tool, or a person can pick up the work from files alone. People approve at four gates; agents never approve their own work.

What I would change in your proposal

Add an orchestrator newSomeone has to route the request, size it, track state, send failures back to the right stage and stop endless loops. Without it, each tool improvises the order.
Test design moves up front newThe business analyst writes acceptance criteria as Given/When/Then scenarios, and a test designer turns them into test cases before any code exists. The developer then codes to known tests, and every requirement is traceable to a test.
Independent code reviewer newThe developer agent should never be the only one to judge its code. A separate reviewer checks it against the design, the repo conventions and the safety rules in AGENTS.md. This is the same maker-checker rule the product already enforces for model releases.
Security and compliance reviewer newInsurance software handles PII and is state-regulated. Tenant isolation, customer-safe projections, audit trails, filed rates and forms, AI data boundaries and secrets need a dedicated check before merge.
Knowledge curator newAI models do not keep learning on their own. "Regularly updates its knowledge" has to be a process: curated knowledge files with sources and review dates, refreshed by a scheduled job that proposes changes for a person to approve.
Unit and automation testing keptBoth stay as separate agents. The unit test agent works next to the developer on unit and integration tests; the automation agent owns API and browser regression suites.
Business user validation changedThe agent prepares the acceptance test script, runs it on staging, and reports evidence against each acceptance criterion. A named business person still signs off. An agent cannot be the business owner.
Deployment agent keptAlso writes release notes, the migration and rollback plan, and checks that the release matches what was approved.

The flow

Solid arrows are the normal path. Dotted arrows send work back when a stage finds a problem; work sent back reopens any approval of the redone work, and a third return to the same stage stops for a person. Diamonds are human approvals; Gates A and B can be waived only in the requester's own words.

The agents

Each card is the core of that agent's contract file in agents/. "Writes" is the handoff file in the work package; the next agent starts from it. Handoff files are numbered by stage: 01 requirements, 02 design, 03 UI design, 04 test design, 05 implementation, 06 unit tests, 07 code review, 08 security and compliance, 09 automation tests, 10 release, 11 end-to-end results, 12 business validation, 13 lessons.

Orchestrator

new

Owns the flow. Sizes the request into a track, creates the work package, decides which agent runs next, and stops loops.

Reads
Your prompt, docs/delivery/WORKFLOW.md, current status.md
Writes
status.md: track, stage, owner, open questions, return count
May not
Write code or approve any gate

Business analyst

1

P&C domain expert. Restates the request in insurance terms, finds gaps, and asks questions before anything is designed.

Reads
P&C knowledge base, docs/DOMAIN.md, GLOSSARY.md, product packs, related issues
Writes
01-requirements.md: business goal, affected lines, states and transactions, rules, numbered requirements, Given/When/Then acceptance criteria, regulatory notes, out of scope
Asks about
Lines and states, transaction types (NB, endorsement, cancel, reinstate, renewal), rating and forms impact, who uses it, compliance
Done when
No open questions; you approve at Gate A

Software architect

2

Knows LatticePolicy's architecture and current industry practice. Chooses the approach and challenges the requirements where the cost or risk is high.

Reads
01-requirements.md, ARCHITECTURE.md, MODULES.md, MULTITENANCY.md, ADRs, architecture knowledge base
Writes
02-design.md: options considered, chosen design, data and migration changes, API contracts, security and tenancy impact, performance, rollout and rollback, ADR if a lasting decision
Done when
Every requirement maps to a design element

UI/UX designer

added

Designs screens, flows, states and wording for any user-facing change with the LatticePolicy design system, WCAG 2.2 AA and insurance UX conventions, before tests are planned and code is written.

Reads
Requirements, design, docs/knowledge/ux/, UI_CONTROL_STANDARDS.md, shared components and tokens
Writes
03-ui-design.md: journeys, screens, wireframes, components, states, wording, accessibility, phone layout; or "No user-facing change"
Done when
Every visible requirement has a designed screen and state; reviewed at Gate B on the major track

Test designer

new

Turns acceptance criteria into test cases at the right layer before coding, using docs/TEST_PLAN.md.

Writes
03-test-design.md: each requirement → unit, integration, API, browser and post-deploy cases; test data; negative and tenant-isolation cases
Done when
Every acceptance criterion has at least one test; you approve design and tests together at Gate B

Developer

4

Knows the codebase and how each AI feature works (submission intake, private document processing, model governance, validation rules). Implements the approved design only.

Reads
Design, test design, AGENTS.md, area docs, existing patterns found with search
Writes
Code on a latticepolicy/ branch, task note in docs/tasks/, doc updates, 04-implementation.md with files changed and any design deviations
May not
Change scope silently, weaken tests, skip safety rules

Unit test agent

5

Writes and runs unit and integration tests from the test design, working alongside the developer.

Runs
npm run test, typecheck, the server integration suite on a fresh database
Writes
05-unit-results.md: tests added, results, coverage of each requirement

Code reviewer

new

Independent of the developer. Reviews the diff for correctness, conventions, simplicity, and drift from the design.

Writes
06-code-review.md: findings ranked by severity, each resolved or sent back
Rule
Started automatically by the orchestrator as a fresh session, separate from the developer

new

Checks tenant isolation and RLS, customer-portal projections, PII handling, secrets, audit trails, AI data boundaries, and regulatory items such as filed rates, forms and notice periods.

Writes
07-security.md

8

Writes

9

Releases through the existing pipelines (publish-ghcr, AWS ECS, Azure Container Apps). Staging first, production only after Gate D.

Writes

11

Walks each acceptance criterion as a business user would, on staging, and records evidence. Prepares the sign-off sheet.

Writes

Hands to

Knowledge curator

new

After release, records lessons learned and updates the knowledge bases. On a schedule, researches industry, regulatory and architecture changes and proposes updates.

Writes
12-lessons.md; pull requests to docs/knowledge/ with sources and review dates
May not
Merge its own knowledge changes

Right-sized tracks

The orchestrator picks a track from the request and tells you which one it chose; you can override it.

TrackUse forAgentsHuman gates
QuickTypos, copy, small bug with an obvious cause, test-only changeOrchestrator, developer, unit test, code reviewer, deploymentC
StandardA feature or behavior change inside one areaAll except the scheduled knowledge refresh; architect writes a short designA, C, D
MajorNew product line, migration, security, tenancy, rating, AI, or cross-module changeAll fourteen, full design with an ADRA, B, C, D

Anything that touches tenant isolation, authentication, rating, filed forms, customer data or AI data boundaries is always Major, whatever its size.

Keeping knowledge current

An AI model's knowledge is fixed when it is trained, and it forgets everything between sessions. Agents stay current only by reading knowledge kept in the repo. I propose three knowledge bases, each file carrying its sources and a last_reviewed date that agents check before relying on it.

Knowledge baseContentsRefresh
P&C insurance
docs/knowledge/pc-insurance/		Lines of business and coverages, policy lifecycle and transactions, rating concepts, forms and ISO/AAIS conventions, ACORD data standards, NAIC model laws, state rules (cancellation and non-renewal notice periods, surplus lines, rate and form filing), claims and billing touchpoints, market trends (CAT exposure, CA/FL property market, cyber)Weekly scan for regulatory and market changes; quarterly full review
Architecture and engineering
docs/knowledge/architecture/		LatticePolicy ADRs, tech radar (adopt, trial, hold), dependency and platform currency (Node, Postgres, React, Playwright), security advisories, cloud reference patterns, AI engineering practiceMonthly; immediately for security advisories
LatticePolicy project
existing docs/		Project context, modules, API, data model, test plan, task notes, handoffsEvery merged change, enforced by the existing task-note rule

The refresh is a scheduled GitHub Actions job that runs the knowledge curator with web research. It opens a pull request listing each proposed change with its source link. A person reviews and merges it. Nothing reaches the agents' knowledge without that review, so a wrong web page cannot quietly change how agents build regulated software.

How it stays tool-neutral

One canonical set of agent contracts lives in agents/. A small sync script generates the thin files each tool looks for, and a CI check fails if they drift.

ToolReadsGenerated from agents/
Codex, Jules, Aider and most agentsAGENTS.mdYes: a "Delivery flow" section pointing to the contracts
Claude CodeCLAUDE.md, .claude/agents/*.mdYes: one subagent per role
GitHub Copilot.github/copilot-instructions.md, .github/prompts/Yes
Cursor.cursor/rules/*.mdcYes
Anything else, or a persondocs/delivery/WORKFLOW.mdCanonical, hand-written

You start a request the same way in any tool:

Start the LatticePolicy delivery flow for: <your request>

Or from a terminal, which creates the work package and prints the prompt for the next agent:

npm run flow -- start "Add mortgagee change endorsement for HO-3"
npm run flow -- status WP-0042
npm run flow -- next WP-0042      # prints the next agent's prompt for any AI tool

Human approvals

GateApprovesEvidence shownDefault approver
ARequirementsRequirements, acceptance criteria, answered questionsYou (product owner)
BDesign and test planDesign, options, risks, test designYou or a lead engineer (Major track)
CMergePR, review and security findings, CI results, traceabilityCode owner (the existing branch protection)
DProduction releaseStaging E2E results, business validation evidence, release and rollback planBusiness owner, plus whoever approves production deploys

Each approval is recorded in status.md with name and date, and the PR check refuses to merge a Standard or Major change without gates A and B recorded.

Rollout

  1. Foundation (done). Agent contracts, WORKFLOW.md, handoff templates, tool adapters with the sync check, and the flow CLI. Trial it on one Standard change end to end.
  2. Knowledge (done). Seed the P&C and architecture knowledge bases from the existing domain primer and docs, with sources and review dates. Add the scheduled refresh job.
  3. Enforcement (done for pull requests). PR check for work packages and gates; staging-first deployment with business sign-off is defined in the contracts and applies from the next release.
  4. Measure. Track returns per stage, defects found after merge, and time per track. Tune the contracts where agents keep failing.

Decisions

The product owner asked for these to be decided by industry practice. They are recorded in docs/delivery/WORKFLOW.md and can be revised there.

Agent autonomyAgents may create branches, commit and open pull requests between gates. They stop at every gate, never merge a pull request and never deploy to production.
ApproversThe product owner approves Gates A, B and D. The code owner approves Gate C through GitHub branch protection. Carrier-specific work adds a carrier business user at Gate D.
Requirements approvalThe orchestrator asks you to approve the requirements by default. If your request says approval is not needed, it records a waiver with your words and continues. Only the requirements and design gates can be waived; merge and business sign-off always need a person.
StagingA persistent staging environment when one is configured; until then the local Docker stack built from main. Tests never use a pilot or demo database.
Knowledge refreshMonthly, from primary sources (state insurance departments, NAIC, ISO/AAIS, ACORD, CAS, NCCI, official release notes, security advisories). A workflow opens an issue; the curator's updates go through a reviewed pull request. Security advisories are handled when they appear.
Code reviewAutomatic and independent. The orchestrator starts the code reviewer itself as a fresh agent session, separate from the developer, so you do not have to do anything. A different model or tool is recommended, not required.
TracksQuick, standard and major as described above.
